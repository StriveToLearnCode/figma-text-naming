# 文本语义词典

本词典用于识别动态文本的业务语义、判断复用关系，并辅助选择 `Page_Module_txtNN` 中稳定的 Page 和 Module。它不是可读 Key 模板；不得从词典直接生成旧式 `<business-domain>/<semantic-key>` Key。

## 身份模型

- 每个文本条目由持久化 UUID 唯一识别。
- 可读 Key 使用 `Page_Module_txtNN`，例如 `tab1_bg1_txt01`，只用于阅读展示和代码引用。
- 代码侧使用 `text/<readableKey>`，例如 `$tf('text/tab1_bg1_txt01', val)`。
- 业务语义决定两个节点是否能共享同一身份，不要求把完整业务含义编码进可读 Key。

## 业务域词表

| 业务域 | 适用语义 | 有效识别证据 |
| --- | --- | --- |
| `lottery` | 抽奖、开奖、抽取次数和抽奖结果 | 图层、组件、区域或相邻标签明确包含抽奖、开奖、转盘、扭蛋等含义 |
| `reward` | 独立奖励模块中的奖励名称、数量和领取状态 | 持久区域明确为奖励、奖品、奖励列表或领奖模块 |
| `task` | 任务进度、完成状态和任务奖励 | 持久区域明确为任务、目标、每日任务或阶段任务 |
| `rank` | 排名、积分和榜单状态 | 持久区域明确为排行榜、名次、积分榜或段位榜 |
| `shop` | 商店中的价格、库存和限购数量 | 持久区域明确为商店、兑换、商品或购买模块 |

业务域优先级为：明确产品或设计命名、稳定组件或区域、同页面已确认的相同功能、基于多项证据的新业务域。不要为单个含义模糊的值创建业务域，也不要用 `板块4` 等位置型容器名代替语义。

业务域可以作为 Module 候选，例如 `lottery` 或 `rank`，但公司文件已有稳定 Module 标识时优先沿用已有标识。Module 的选择与文本语义复用是两项独立判断。

## 标准语义词表

| 标准词 | 运行时含义 | 常见中文证据 |
| --- | --- | --- |
| `current-count` | 当前已经拥有、使用或发生的次数 | 当前次数、已有次数、已抽次数 |
| `remaining-count` | 仍可使用或尚未完成的次数 | 剩余次数、可用次数、还可抽 |
| `total-count` | 总次数或累计数量 | 总次数、累计次数、总数量 |
| `countdown` | 随时间递减的剩余时长 | 倒计时、剩余时间、距开启 |
| `progress` | 当前进度值或进度比例 | 当前进度、完成进度、幸运值进度 |
| `multiplier` | 奖励、得分或产出的倍率 | 倍数、倍率、翻倍 |
| `name` | 业务域本身所指对象的名称 | 独立奖励模块中的奖励名称 |
| `count` | 业务域本身所指对象的数量 | 独立奖励模块中的奖励数量 |
| `reward-name` | 当前奖励或奖品的名称 | 奖励名称、奖品名称、获得物品 |
| `reward-count` | 当前奖励或奖品的数量 | 奖励数量、奖品个数、获得数量 |
| `current-rank` | 当前用户或条目的名次 | 当前排名、我的名次、当前段位 |
| `score` | 排行或任务使用的积分值 | 积分、分数、榜单分值 |
| `price` | 商品购买或兑换所需的价格 | 价格、售价、兑换消耗 |
| `stock` | 商品当前库存 | 库存、剩余库存 |
| `completed` | 已完成状态 | 已完成、任务完成 |
| `claimed` | 奖励已领取状态 | 已领取、领取完成 |
| `locked` | 尚未解锁状态 | 未解锁、尚未开启 |

`name` 和 `count` 只在业务域已经唯一说明对象时使用。`current-count`、`remaining-count` 和 `total-count` 不得互换。文本只有 `xx` 时，必须从图层名称、语义祖先或相邻标签取得限定信息，否则标记为低置信度。

## 组件语义模式

| 组件 | 可复用语义 |
| --- | --- |
| 抽奖 | 当前抽奖次数、剩余抽奖次数、抽奖倒计时、奖品名称 |
| 奖励 | 奖励名称、数量、领取状态 |
| 任务 | 任务进度、任务奖励数量、完成状态 |
| 排行 | 当前名次、榜单积分 |
| 商店 | 商品价格、库存、剩余可购次数 |

组件模式只在业务证据成立时使用。文案出现“奖励”不代表业务域一定是 `reward`；抽奖模块中的奖品名称仍属于抽奖上下文。业务语义相同且渲染、状态、数据来源及占位符顺序一致时可以复用身份；任一项不同都不得复用。

## 旧格式兼容

`u32fEVPo` 页面历史上出现过 `txt/progress`、`txt/treasury`、`txt/had-send`、`txt/times`、`txt/lottery`。这些值只作为旧数据识别线索：

- 不得将它们作为新可读 Key 的模板。
- 不得在仅扫描 Figma 时自动迁移或删除。
- 如权威配置要求继续兼容，原样报告旧 UUID、旧 Key 和语义，交由有配置写权限的迁移流程处理。
- 新命名使用 `Page_Module_txtNN`，并为代码侧生成 `text/<readableKey>`。

## 设计侧证据

- 动态文本图层的原有名称只有在明确描述中文业务含义时才构成证据，例如 `当前抽奖次数`、`奖励倍数`、`商品库存`。
- 纯数字或占位符文本不得只依赖 `数字`、`文案`、`xx` 判断语义。
- `Frame 123`、`Group 8`、`板块4`、`文本`、`数字` 等名称不构成业务语义证据。
- 生成的图层名必须使用公司可读 Key 格式，不再把英文业务域路径写入图层名称。

## 词条治理

按以下顺序选择语义词：完整匹配的组件模式、词典标准词组合、基于明确证据的新建议词。不得为了避免冲突而发明同义词。

仅在语义已经成为稳定复用组件的正式含义，或至少在两个独立页面中以相同含义重复出现时，才把新词加入词典。新增词条必须记录唯一英文词、中文含义和识别证据。孤立或含义不清的文本应标记为低置信度并等待确认。
