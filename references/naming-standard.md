# Figma 特效文本命名规范

本文件是 `figma-text-naming` 的命名事实源，统一规定扫描范围、候选检测、去重、业务 Key、中文含义、样式编号、冲突和稳定性。

## 1. 扫描范围

任何可访问的 Figma 文件、页面或节点都可以作为扫描入口，不要求页面名、Frame 名或节点类型符合特定格式。

根据用户链接确定扫描根节点：

- 链接包含 `node-id` 时，以该节点本身作为扫描根节点，不自动提升到父级。
- `node-id` 指向 `TEXT` 时，只扫描该节点本身。
- `node-id` 指向页面或容器时，扫描该节点的全部后代。
- 链接未提供 `node-id` 时，扫描文件内全部可访问页面。
- 多个链接合并后按节点 ID 去重；一个根节点已包含另一个时，只保留范围更大的根节点。
- 节点不存在、无权访问或无法读取时，记录失败，不得静默扩大范围。

扫描根节点本身及其全部后代 `TEXT`，包括隐藏节点。

当前名称已经合法的候选仍须参与扫描。链接已经限定节点时，其父级、同级和范围外节点不得纳入。同一页面内，本次选中的多个扫描根节点可以共同去重，但不得跨页面自动去重。

实例继承或只读文本可以记录，但不得直接改名。

## 2. 候选检测

使用文本节点的 `characters` 判断是否包含动态占位符，不使用当前图层名称：

```js
const dynamicPlaceholder = /(^|[^A-Za-z0-9])(?:[xX]{2,}|X)(?=$|[^A-Za-z0-9])/;
const isCandidate = dynamicPlaceholder.test(node.characters);
```

可以识别：

```text
xx时xx分
xxxx/100
XX
独立大写 X
```

不匹配：

```text
1x
box
extra
```

当前名称已符合格式的文本仍须参与候选检测，用于复核语义、去重关系和名称冲突。

## 3. 文字与样式去重

两个候选只有同时满足以下条件时，才视为相同文本：

1. 规范化后的文字完全一致。
2. 规范化后的有效文字样式完全一致。

### 文字签名

为每个候选生成 `textSignature`。比较前只进行：

- Unicode 统一为 NFC。
- CRLF 和 CR 统一为 LF。
- 每个动态占位符统一表示为 `{{}}`。
- 清理不影响展示的行尾空白。

除此之外不修改正文。文字内容、占位符数量、位置、顺序、换行、正文空格或标点任一不同，都视为文字不同。

### 样式签名

只为 `textSignature` 相同的候选生成 `styleSignature`。当前至少记录：

- 文字颜色。
- 字号。
- 字重。
- 每段样式实际作用的字符范围。

等价颜色统一为相同颜色值，字号统一为相同数值单位，字重统一为规定数值，连续且完全相同的样式片段合并。

样式值、作用范围、片段顺序或占位符样式任一不同，都视为样式不同。即使颜色值相同，一个节点只给占位符着色、另一个给整句着色，也属于不同样式。

### 比较流程

1. 先生成并比较 `textSignature`。
2. 文字不同的候选直接判定为 `different`。
3. 将文字相同的候选分组并批量读取 styled text segments。
4. 在组内比较 `styleSignature`。
5. 文字和样式都相同的候选归为同一组。
6. 样式不同的候选拆为不同组。

以下信息不得进入 `textSignature` 或 `styleSignature`：

- 当前图层名称、候选 Key、页面 ID、节点 ID。
- Frame、父级路径、组件、变体、区域和视觉位置。
- 节点顺序、可见性、业务语义和中文翻译。

这些信息可以用于命名、排序或定位，但不得改变去重结果。不得因为位置不同而拆开相同文字，也不得因为业务含义相近而合并不同文字。

### 无法比较

出现以下情况时返回 `confirm`：

- styled text segments 缺失。
- 样式片段无法覆盖全部字符。
- 样式片段范围重叠或顺序异常。
- 无法确定样式实际作用范围。
- 样式数据冲突或无法排除有意义的差异。

去重结果只使用：

- `same`：文字和样式都完全一致。
- `different`：文字或样式至少一项不同。
- `confirm`：样式数据不足或无法可靠比较。

## 4. 名称格式

名称用于稳定识别业务字段，不用于描述图层位置、视觉样式或完整句子。

完整格式：

```text
<business-domain>/<semantic-key>
```

新名称必须通过：

```js
const canonicalTextKey =
  /^[a-z][a-z0-9]*(?:-[a-z0-9]+)*\/[a-z][a-z0-9]*(?:-[a-z0-9]+)*$/;
```

要求：

- 只能包含一个 `/`。
- 两段都非空。
- 全小写和 kebab-case。
- 使用正确英文拼写。
- 一个稳定业务域和一个语义字段。

禁止 camelCase、下划线、大写字母、无语义数字、历史错拼、节点 ID、Frame 序号、坐标和区域编号。

禁止：

```text
coinPool/share-count
tab1/screen_tips
tab2/level_remain_time
signSuccess/reward
tab1/getTimes
```

## 5. 业务域与语义字段

`business-domain` 表示文本直接所属的稳定业务对象或功能模块，例如：

```text
lottery
reward
team
ranking
founder
level
medal
puzzle
recharge
sign
share
broadcast
```

业务域不得来自页面位置、Tab 序号、Frame、区域标识、颜色、样式、节点 ID、音译或扫描顺序。

业务对象明确时，不得使用：

```text
txt
text
page
tab1
tab2
info
bottom
```

只有文本确实描述通用弹窗、提示或界面能力，且无法归属于更具体对象时，才可以使用 `dialog` 或 `toast`。

`semantic-key` 表示字段核心含义、状态或业务动作，通常使用 1–4 个必要英文词，例如：

```text
remaining-count
current-rank
guarantee-progress
purchase-confirm
unlock-confirm
reward-name
seat-status
```

名称不逐句翻译完整文案。例如：

```text
确认花费 {{}} 个抽奖币抽奖 {{}} 次吗？
```

使用：

```text
lottery/confirm
```

不要堆叠为完整句子的逐词翻译。

## 6. 标准词义

### 数量

统一使用 `count`，不新建 `num`、`times`、`val`。按需补充被计数对象：

```text
reward/count
vote/remaining-count
ranking/voter-count
lottery/remaining-draw-count
```

### 剩余

统一使用 `remaining`，不新建 `remain` 或 `left`：

```text
gift/remaining-count
level/remaining-time
```

### 余额

可消费资源当前拥有量使用 `balance`。纯数量展示、不表达用户当前持有余额时使用 `count`。

### 进度

当前值与目标值之间的过程使用 `progress`。只有明确是保底进度时才保留 `guarantee`。

### 排名

排名位置使用 `rank`。排行榜整体模块可以使用 `ranking`：

```text
founder/current-rank
ranking/friend-rank
ranking/national-rank
```

### 时间

按真实含义区分：

```text
duration
countdown
remaining-time
start-time
end-time
```

### 状态与结果

当前状态使用 `status`。具体身份、等级或阶段使用真实对象。操作结果使用 `success` 或 `failure`，需要时补充动作对象。

### 确认操作

二次确认文案使用动作加 `confirm`：

```text
lottery/confirm
chip/purchase-confirm
dialog/unlock-confirm
sign/compensation-confirm
```

### 名称、标题与编号

根据真实字段含义选择 `name`、`title` 或 `number`。显示 `NO.{{}}` 时仍应依据业务含义判断是否为 `seat-number`、`ring-number` 等具体字段。

## 7. 命名证据

名称只能依据当前 Figma 中可观察的信息确定，按以下顺序使用：

1. 完整原文及占位符结构。
2. 与候选唯一对应的中文备注。
3. 当前图层名称。
4. 最近的具名业务父节点或祖先。
5. 相邻标签和兄弟文案。
6. 所属组件及变体状态。
7. 同页已经确认的平行字段。

当前名称只能作为参考，不能反向证明自身正确。`Frame 123`、`Group 8`、`Text 128`、`板块4`、`数字`、`xx` 等自动或空泛名称不构成有效语义证据。

中文备注必须能通过同组、邻接、标注连线、配对结构或其他明确关系唯一对应。备注与原文冲突时标记 `confirm`。只有占位符且无法确定业务含义时同样标记 `confirm`。

局部样式只用于去重和区分样式版本，不得用于推断业务域或字段语义。

## 8. 中文含义

中文含义必须忠实翻译完整原文：

- 保留完整信息。
- 占位符统一表示为 `{{}}`。
- 保留数量、状态、时间、条件和否定关系。
- 不增加原文没有的信息。
- 不将完整句子概括为“奖励名称”“条件文案”等摘要。

中文含义表达完整原文；英文名称只表达字段核心语义。

## 9. 名称选择

### 复核当前名称

当前名称同时满足以下条件时保持不变：

- 符合标准格式。
- 业务域和字段语义准确。
- 与去重结果和样式编号一致。
- 当前扫描范围内不存在名称冲突。

不得仅因为存在更短或更常见的近义名称，就替换已经准确、稳定的当前名称。

### 参考同页平行字段

当前名称不可用时，可以参考同页已经确认的平行字段，但只能复用稳定业务域和语义结构，不得按单个相同单词机械套用。

### 创建新名称

新名称必须使用明确业务域和完整英文词，保持简短，能区分同页其他字段，且不包含位置或样式信息。

无法可靠确定业务域或字段含义时标记 `confirm`，不得使用 `txt`、`text`、`value`、`info` 等通用词猜测。

## 10. 样式版本编号

文字和样式都相同的候选共用一个名称，不增加编号。

文字相同、业务语义相同但样式不同的候选，可以使用共同基础名称加两位编号：

```text
ring/box-open-count-01
ring/box-open-count-02
```

编号只表示同一字段的不同样式版本，不表示 Frame、页面区域、组件位置、视觉位置或节点顺序。只有文字和业务语义都能确认相同时，才允许建立样式编号组。

已有编号与对应样式稳定匹配时保持不变。新增版本使用组内未占用的最小两位编号。首次分配时按规范化样式签名稳定排序；样式签名相同时，再使用页面顺序和节点 ID 稳定裁决。排序信息不得进入名称。

## 11. 名称冲突

### 相同名称对应不同候选组

相同名称对应不同文字、不同业务字段或未建立样式编号关系的不同样式组时，属于冲突。

不得通过追加节点 ID、Frame 编号、区域编号、坐标或扫描顺序解决冲突。应根据真实语义重新命名，无法区分时标记 `confirm`。

### 同一候选组存在多个名称

- 只有一个名称合规时使用它。
- 多个名称合规且语义等价时，优先保留组内使用更多的名称。
- 使用数量相同时，优先保留更准确、完整且不含兜底词的名称。
- 仍无法稳定选择时标记 `confirm`。

不得为了保留全部旧名称而将相同候选拆成多个组。

### 格式正确但语义错误

正则匹配不代表名称正确。业务域错误、字段语义错误、名称过度概括、无依据的位置或编号、错误拆组或错误共名都不可用。

用户明确指定的名称也必须通过格式、语义、去重关系、样式编号和名称冲突检查。

## 12. 稳定性

已有名称符合规范、语义准确且不存在冲突时，不得因为以下原因重新命名：

- 扫描顺序变化。
- 图层移动。
- Frame 折叠或展开。
- 节点隐藏或显示。
- 选中状态变化。
- 新增无关节点。
- 查询返回顺序变化。

文本内容、占位符结构、有效局部样式或业务语义发生变化时，重新复核名称。
