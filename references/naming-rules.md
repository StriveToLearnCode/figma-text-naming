# 命名规则

本文件负责识别需要命名的动态文本，并为去重后的候选组选择稳定、准确的业务 Key。

文本与样式是否相同，由 [deduplication.md](deduplication.md) 判断。本文件不负责生成富文本、修改 Figma 或定义用户汇报格式。

## 候选项检测

使用文本节点的 `characters` 判断是否包含动态占位符，不使用当前图层名称：

```js
const dynamicPlaceholder = /(^|[^A-Za-z0-9])(?:[xX]{2,}|X)(?=$|[^A-Za-z0-9])/;

const isCandidate = dynamicPlaceholder.test(node.characters);
```

该表达式可以识别：

```text
xx时xx分
xxxx/100
XX
独立大写 X
```

不匹配：

```text
1x
box
extra
```

当前名称已经合法的文本仍须参与扫描，用于复核语义、去重关系和名称冲突。

## 名称格式

名称格式为：

```text
<business-domain>/<semantic-key>
```

只能包含一个 `/`。

新名称必须通过：

```js
const canonicalTextKey =
  /^[a-z][a-z0-9]*(?:-[a-z0-9]+)*\/[a-z][a-z0-9]*(?:-[a-z0-9]+)*$/;
```

已批准先例可以保留历史 camelCase、业务数字或历史拼写，但必须精确存在于 [approved-name-corpus.md](approved-name-corpus.md)。

兼容性检查可以使用：

```js
const compatibleTextKey =
  /^[a-z][a-z0-9]*(?:-[a-z0-9]+)*\/[a-z][A-Za-z0-9]*(?:-[A-Za-z0-9]+)*$/;
```

`compatibleTextKey` 只表示系统能够承载该格式，不能用于批准新的 camelCase 名称。

例如以下名称只能在复用已批准先例时保留：

```text
lottery/chipShort
lottery/chip1Short
build/singleSuccess
broadcast/text2
pullup/progcess
```

新生成的名称必须使用全小写 kebab-case 和正确英文拼写。

## 名称语义

### 业务域

`business-domain` 表示稳定的业务对象或模块，例如：

```text
lottery
reward
ring
rank
broadcast
achievement
```

业务域不得来自：

- 页面位置；
- Frame 名称或序号；
- 坐标；
- 158、388 等区域标识；
- 节点 ID；
- 颜色；
- 中外文音译。

### 语义字段

`semantic-key` 表示文本字段的核心含义，通常使用 1 至 3 个简短英文词。

例如：

```text
lottery/remaining-draw-count
ring/box-open-count
reward/name
rank/score
```

名称只需要区分字段，不逐句翻译完整文案。

仅在确有区分意义时保留状态、数量或时间等信息，例如：

```text
remaining
completed
count
countdown
```

`chance` 表示机会，`count` 表示数量。只有需要同时表达两层含义时才使用：

```text
open-chance-count
```

能够使用更短名称时，不增加多余词语。

不得在语义已经明确时使用以下词语作为无依据兜底：

```text
txt
text
value
info
page
```

已批准先例或明确组件语义中的这些词可以保留。

## 命名证据

名称只能根据当前目标 Figma 页面的可观察信息确定，按以下顺序使用：

1. 完整原文及占位符结构；
2. 与该文本明确对应的中文备注；
3. 当前图层名称；
4. 最近的具名语义父节点或祖先；
5. 相邻标签或兄弟文案；
6. 所属组件及变体状态；
7. 同页中语义已经确认的合法名称。

中文备注只有在能够通过同组、邻接、标注连线、配对命名或其他结构唯一对应时才可使用。

不能仅因为某段中文位于附近，就认定它是当前文本的备注。

以下名称不构成有效语义证据：

```text
Frame 123
Group 8
板块4
Text 128
数字
xx
```

只有占位符且其他上下文也无法说明含义时，标记为 `confirm`。

中文备注与原文含义冲突时，也标记为 `confirm`。

局部样式只能用于判断候选是否属于不同文本组，不能决定业务域或字段语义。

## 中文含义

中文含义必须忠实翻译完整原文。

- 原文是什么意思，就翻译成什么意思；
- 保留原文中的数量、状态、时间、否定和条件关系；
- 占位符统一保留为 `{{}}`；
- 不根据业务上下文补充原文没有的信息；
- 不把完整翻译缩写成“奖励名称”“条件文案”等摘要。

中文含义和英文名称分别处理：

- 中文含义用于表达完整原文；
- 英文名称只表达字段核心语义。

## 名称选择顺序

为每个去重后的候选组按以下顺序选择名称。

### 1. 复核当前名称

当前名称同时满足以下条件时，保持不变：

- 格式合法，或精确存在于已批准先例；
- 业务域与当前文本一致；
- 字段语义与当前文本一致；
- 与去重和编号关系一致；
- 当前页面内不存在名称冲突。

不得仅因为先例库中存在另一个近义名称，就替换当前合法名称。

当前名称只是一项证据，不能反向证明其语义正确。

### 2. 复用批准先例

当前名称不可用时，查询 [approved-name-corpus.md](approved-name-corpus.md)。

业务域、字段语义和用途都一致时，原样复用完整先例。

例如：

```text
lottery/chipShort
```

不得改写为：

```text
lottery/chip-short
```

业务域不同但字段语义相同时，可以参考语义词，但不能直接照搬完整名称。

先例中的 camelCase、业务数字或历史错拼只能在复用对应完整先例时保留，不得拆开重新组合。

多个先例都可能匹配且无法通过 Figma 上下文确认时，标记为 `confirm`。

### 3. 创建新名称

没有可复用名称时，生成新的全小写 kebab-case 名称。

不得创造：

- 新的 camelCase；
- 无业务语义的数字；
- 历史错拼；
- 区域编号；
- 节点编号；
- 扫描顺序编号。

无法从 Figma 证据中可靠确定业务域或字段含义时，标记为 `confirm`，不得使用通用词猜测。

## 相同文字的样式编号

根据 [deduplication.md](deduplication.md)：

- 文字和样式都相同的候选属于同一组，共用一个不带自动编号的名称；
- 文字相同但样式不同的候选属于不同组，可以使用共同基础名称加两位编号区分。

例如：

```text
ring/box-open-count-01
ring/box-open-count-02
```

编号只表示同一文案的不同样式版本，不表示：

- 158 或 388 区域；
- Frame；
- 组件位置；
- 视觉顺序；
- 节点顺序。

只有候选具有相同规范化文字和共同业务语义时，才可以建立样式编号组。

多个文本都只显示 `xx`，但无法确认业务含义相同，不得直接命名为：

```text
txt/01
txt/02
```

也不得把语义不同的文本放进同一编号组。例如：

```text
rank/score
lottery/remaining-draw-count
```

应分别命名，不应使用同一个基础名称加编号。

### 编号稳定性

已有合法编号与对应样式稳定匹配时，保留原编号。

新增样式版本使用当前组内未占用的最小两位编号：

```text
-01
-02
-03
```

不得因为以下变化重新排列已有编号：

- 重新扫描；
- 节点移动；
- Frame 或组件变化；
- 158、388 等区域变化；
- 视觉顺序变化；
- 新增其他成员。

整组首次编号且不存在已有编号时，按规范化样式签名稳定排序；样式签名相同时，再使用 Frame 页面顺序和节点 ID 裁决。

排序只用于首次编号，不进入名称语义。

已批准先例中的业务数字不属于样式编号，例如：

```text
broadcast/text2
lottery/chip1Short
build/cong1
achievement/has-chip3
mod12/choose-name
```

只有语义和用途与对应先例一致时，才能保留这些数字。

若 `broadcast/text2` 存在两个样式版本，应命名为：

```text
broadcast/text2-01
broadcast/text2-02
```

## 名称冲突

以下情况属于名称冲突：

### 相同名称对应不同内容

同一名称对应不同文字或不同样式组时，不得继续复用该名称。

不得通过追加节点 ID、区域编号、Frame 编号或视觉位置解决冲突。

应重新选择语义准确的名称；无法可靠选择时标记为 `confirm`。

### 相同候选组存在多个合法名称

同一个去重组中存在多个不同且格式合法的当前名称时，不自动选择其中任何一个，也不因某个名称更接近批准先例而静默覆盖其他名称。

将该组标记为 `confirm`，等待确认应保留的名称。

### 名称格式合法但语义不正确

正则通过不代表名称正确。

以下情况仍视为不可用：

- 业务域与实际内容不一致；
- 字段语义错误；
- 名称过度概括；
- 名称包含无依据的区域或编号；
- 应当共享名称的节点被拆分；
- 不同文本错误共用同一名称。

用户明确指定的名称也必须通过格式、语义和当前页面冲突检查。用户为某一节点指定名称，不构成其他节点的命名证据。

## 稳定性

已有名称合法、语义准确且没有冲突时，不得因为以下原因重新命名：

- 扫描顺序变化；
- 图层移动；
- Frame 折叠或展开；
- 节点隐藏或显示；
- 选中状态变化；
- 新增无关节点；
- 批量查询返回顺序变化。

文本内容、占位符结构、有效样式或业务语义发生变化时，重新复核名称。
