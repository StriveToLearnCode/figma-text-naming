# 命名规则

## 候选项检测

使用文本节点的 `characters`，不使用当前图层名称：

```js
const dynamicPlaceholder = /(^|[^A-Za-z0-9])(?:[xX]{2,}|X)(?=$|[^A-Za-z0-9])/;
const isCandidate = dynamicPlaceholder.test(node.characters);
```

该表达式可匹配 `xx时xx分`、`xxxx/100`、包含 `XX` 的阿拉伯语文本及独立大写 `X`，但不匹配 `1x`。当前名称合法的候选仍要扫描，用于复核语义、冲突和去重关系。

## 名称格式

```js
const canonicalTextKey = /^[a-z][a-z0-9]*(?:-[a-z0-9]+)*\/[a-z][a-z0-9]*(?:-[a-z0-9]+)*$/;
const compatibleTextKey = /^[a-z][a-z0-9]*(?:-[a-z0-9]+)*\/[a-z][A-Za-z0-9]*(?:-[A-Za-z0-9]+)*$/;
```

格式为 `<business-domain>/<semantic-key>`，且只能有一个 `/`。一个名称只有在精确存在于 [approved-name-corpus.md](approved-name-corpus.md)，或通过 `canonicalTextKey` 时才算格式合法。`compatibleTextKey` 只用于检查先例能否被系统承载，不能批准先例表之外的 camelCase。先例按原样保留，例如 `lottery/chipShort`、`build/singleSuccess`。正则只校验结构，不能证明语义正确。

- 业务域描述稳定业务对象或模块，不描述页面位置。
- 语义部分只表达字段的核心含义，优先使用 1 至 3 个简短英文词。
- 只保留识别字段所需的对象、数据类型或状态，不逐句翻译完整文案。
- 页面位置、坐标、Frame 序号等非语义上下文不进入名称。
- `txt`、`text`、`page`、`value`、`info` 等通用词在已批准先例或明确 Figma 组件上下文中可以使用，但不得在业务域和字段含义已明确时当作无依据的兜底词。
- 不使用颜色、坐标、Frame 序号或中外文音译。

## 先例优先与兼容边界

把 [approved-name-corpus.md](approved-name-corpus.md) 视为项目已批准先例，而不是可随意拆词组合的词袋：

1. 候选的业务域和字段语义与某条先例一致时，原样复用完整名称。
2. 只有字段语义一致、业务域不同时，只复用确切语义词，不照搬完整名称。
3. `chipShort`、`singleSuccess` 等 camelCase，`chip1Short`、`text2`、`cong1` 等内嵌数字，以及 `progcess` 等历史拼写，只能在复用对应先例时原样保留。
4. 新造名称使用全小写 kebab-case 和正确英文拼写，不主动创造新的 camelCase、无语义数字或历史错拼。
5. 不为“统一风格”改写已匹配的先例，例如不得把 `lottery/chipShort` 改成 `lottery/chip-short`，也不得把 `pullup/progcess` 改成 `pullup/progress`。

先例优先不等于见词即套用。只有 Figma 文本、中文备注、父级/组件上下文能够共同证明同一用途时才匹配；证据不足时进入 `confirm`。

正则匹配只是最低条件。业务域、语义、编号和共享关系也必须符合本文件及去重规则。

## 中文含义与英文名称

中文含义和英文名称分开处理：中文含义直接翻译原文，原文是什么意思就写什么意思，不根据业务上下文补充、概括或扩写；英文名称只提取可识别字段的核心语义，保持简短稳定。

- 原文包含数量、状态、时间、否定或条件关系时，中文含义如实翻译。
- 英文名称只在这些信息用于区分字段时保留对应词，例如 `count`、`remaining`、`completed` 或 `countdown`。
- `chance` 表示机会，`count` 表示数量；需要区分时使用 `open-chance-count`，不需要时使用更短的 `open-chance`。

## Figma 语义证据

命名依据只来自当前目标 Figma 页面的可观察快照，按以下顺序使用：

1. 完整文本及占位符在文本中的数量、位置和顺序。
2. 与候选文本明确对应的中文备注。
3. 写回前有明确业务含义的图层名称。
4. 最近的具名语义父节点或祖先。
5. 相邻标签和兄弟文案。
6. 所属组件、组件或变体状态。
7. 同页同语义组中已由上述证据确认的合法名称。

“明确对应”必须能从同组、邻接、标注连线、配对命名或其他可观察结构唯一确认，不能仅因附近出现中文文本就视为备注。中文备注只用于校验原文含义；与原文冲突时标为 `confirm`。

`Frame 123`、`Group 8`、`板块4`、`Text 128`、`数字`、`xx` 等自动或空泛名称不构成语义证据。只有占位符且上下文不能说明含义时进入 `confirm`。

首次扫描使用文本、明确关联的中文备注、写回前名称和精简 `parentPath`。若工具不能直接返回备注，或备注与候选节点的对应关系不明确，将相关候选合并到第二阶段的一次批量查询中确认。直接祖先、相邻文案、组件、变体和局部样式只在这些字段不能解决实际歧义时补查。

每个候选默认读取生成富文本所需的 styled text segments；同一规范化文本出现多次时，合并前必须比较会影响最终展示的局部样式。颜色、字号或字重等局部样式差异不能决定业务语义或业务域，但会决定相同文本是否需要使用不同编号名称。富文本按主流程从 Figma 样式片段生成最小 `<span>`，不得改用设计稿转代码结果或猜测样式。Frame、组件区域、158/388 标识和视觉位置不得影响该结论。

## 选择顺序

1. 根据完整原文写中文含义；有明确对应的中文备注时用于校验。
2. 从原文和 Figma 上下文提取字段的核心语义与业务域，查询已批准先例。
3. 存在语义和用途都匹配的先例：原样复用；多个先例均可能匹配时，用组件/父级上下文消歧，否则进入 `confirm`。
4. 没有匹配先例时，当前名称或同页已有名称若通过 `canonicalTextKey`、简短且语义、用途、编号与去重关系一致，则保留或复用。
5. 仍无可用名称时，生成简短的全小写 kebab-case 名称；Figma 证据不足或冲突时进入 `confirm`。

已有名称只是一项待复核证据，不能反向证明语义正确。已有 `txt/progress` 等合法短名称可在符合通用规则时保留；若与可观察语义不一致则进入 `confirm`。用户明确指定名称时，也必须通过格式、当前页面内冲突和语义一致性校验；该指令不作为其他节点的命名证据。

## 编号

优先使用不带自动样式编号的名称。规范化文字、占位符结构和有意义的局部样式完全相同时共用同一个名称，不追加 `-01`、`-02`。

先例中的数字可能属于稳定业务语义，例如 `broadcast/text2`、`lottery/chip1Short`、`build/cong1`、`achievement/has-chip3`、`mod12/choose-name`。语义和用途匹配时保留这些数字；只有同页平行节点和明确的变体/序号证据都支持时，才可沿用同一业务编号模式。不得把业务数字误判成样式编号，也不得仅按扫描顺序生成业务数字。

只有多个节点的规范化文字和占位符结构相同、具有共同语义，但有意义的局部样式不同时，才在共同语义后加编号：

```text
reward/name-01
reward/name-02
ring/box-open-count-01
ring/box-open-count-02
```

- 不得因为多个文本都显示 `xx` 就建立编号组。
- 排行积分和剩余抽奖次数不是同类，应分别使用 `rank/score`、`lottery/remaining-draw-count` 等语义名称。
- 中文备注均为“戒指盒开启次数”的两个节点，在文字和局部样式相同时统一使用 `ring/box-open-count`；只有样式不同时才使用 `ring/box-open-count-01`、`ring/box-open-count-02`。
- 已有合法、语义正确且与样式版本稳定对应的自动编号尽量保留。新增样式版本使用组内未占用的最小两位编号，不因扫描顺序、Frame、组件区域、158/388 标识或视觉位置变化重排。
- 自动添加的两位编号只区分同类文本的样式版本，不得表达业务区域。
- 自动编号前必须有共同语义；禁止 `txt/01`、`txt/02`、`text-01`、`Page_Module_txt01`。

## 冲突与稳定性

- 相同名称对应不同文本结构或有意义的局部样式时是冲突，不得静默复用或用节点标识、区域编号消除冲突。
- 格式正确但语义错误、过长或共享关系错误的名称仍需确认。
- 不得因扫描顺序、图层移动、Frame 折叠、隐藏或新增无关节点重命名已有合法项。
- 首次分配需要排序时，依次使用 Frame 页面顺序、层级/视觉顺序和节点标识；排序只用于稳定裁决，不进入名称。
